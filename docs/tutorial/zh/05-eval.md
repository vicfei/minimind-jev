# 第 5 章 · 评测：接基准协议，对比表怎么读

模型好坏不由训练曲线说了算。我们把它接到 [jev-rag-zh-benchmark](https://github.com/vicfei/jev-rag-zh-benchmark) 的协议上——和 hosted Jev、BM25 用**同一个样本、同一套指标、同一种置信区间**比。

## 协议三要素

1. **同样本**：s1 = 100 个查询 × (1 正 + 9 难负)。评测查询在第 1 章就被排除出训练集——零泄漏是表上数字合法的前提。
2. **同指标**：nDCG@5——正例段落被排在第几位。10 个候选里正例排第 1 得 1.0，掉出前 5 得 0。MRR、Recall 同理。
3. **同置信区间**：对查询做 bootstrap 重采样（1000 次）算 95% CI；系统间比较用**配对差**（同一批查询上逐个相减再 bootstrap）——配对消掉了"题目难度"这个公共方差，比直接比较两个区间敏感得多。

## 六方表逐行读

| 系统 | nDCG@5 | 怎么读 |
|---|---|---|
| hosted Jev score-zh | 0.546 | 点估计最高，但—— |
| hosted Jev noul-zh | 0.531 | 与 score 版几乎打平：纯排序任务二值问题就够（基准仓的独立发现） |
| **minimind-jev v0.1** | **0.488** | 配对 −Jev 差 [−0.040, +0.157] 含零 → **统计不可分**；配对 +BM25 [+0.002, +0.154] 不含零 → **真赢 BM25** |
| v0.3-lite | 0.440 | 与 BM25（+0.027 [−0.050, +0.102]）和 v0.1（−0.048 [−0.134, +0.037]）**都不可分** |
| v0.2 蒸馏 ×3 | 0.428-0.430 | 对 v0.1 的配对差 CI **不含零** → **真输**（第 6 章的主题） |
| BM25 | 0.413 | 下界参照 |

三条读表纪律：

- **CI 含零 ≠ 相等**。v0.1 对 Jev"不可分"只说明 n=100 分不出 0.06 的差距——可能是没差距，也可能样本再大就分出来了。不可分声明的是证据强度，不是等号。
- **点估计排序 ≠ 显著性排序**。v0.3-lite（0.440）高于蒸馏（0.428-0.430）但三者互相都不可分；而蒸馏对 v0.1 的落后是显著的。
- **知道自己在跟谁比**。v0.1 的"不可分"对象是 $0.042/M token 的商业模型，成本侧是 3 分钟笔记本训练——把两边都摆出来才是完整的陈述。

## 分离度与排序的分歧：一个精彩的误差结构

v0.3-lite 的分离度 **AUC 0.647 高于 v0.1 的 0.630**，排序 nDCG 却更低（0.440 vs 0.488）。这两个指标测的不是一回事：AUC 统计所有正负对的相对顺序（全局成对判断），nDCG 只在乎**正例在自己池内的名次**（局部榜位）。一个模型可以整体成对判断不错，但在具体池里把正例压在三四名——重排场景要的恰恰是榜位。选指标就是选你优化的东西。

## 一次差点发出去的假数字（工程教训）

第一次对接评测时，导出脚本写的日志信封是 `answer.answers.answers`（三层），而基准的解析器读 `answer.answers`（两层）。解析器不报错——它把所有分数读成 None，然后**按候选池的原始顺序排序**，产出一张看起来完全正常的表：nDCG 0.328、各指标都有值。破绽只有一处：**separation 行整个消失了**（没有分数就没有 AUC），外加 R@1=0.12 恰好等于随机。抓住它靠的不是运气，是"数字先过 sanity 再出仓"：随机基线是多少、缺了哪行、量级对不对。

兼容层的教训：**接口对齐错误在数值管道里是静默的**，必须在消费端断言"我真的读到了非空数据"。
